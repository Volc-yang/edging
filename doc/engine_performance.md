# Godot 与 UE5 第一章消费端性能对比

采集时间：2026-09-21
采集脚本：`python3 tools/benchmark_consumers.py --runs 3 --json <输出>`
机器：MacBook Pro M4 Pro / 48 GB / macOS 26.6.2
快照：`models/chapter_one_snapshot.json`（两轮均确认消费成功，各自打印了 VALID 标记）

## 一、实测数据

| 指标 | Godot 4.7.2 | UE5 5.8.2 | 倍数 |
|---|---:|---:|---:|
| headless 单轮耗时（中位） | **0.244 s** | **10.606 s** | UE5 慢 **43×** |
| 耗时区间 | 0.237–0.253 s | 10.593–10.617 s | — |
| 峰值内存 RSS | **217.8 MB** | **1723.4 MB** | UE5 高 **7.9×** |
| 引擎安装体积 | 337 MB | **43 GB** | UE5 大 **128×** |
| 第一章工程载荷（源码+配置） | 60 KB（GDScript + 场景 + 工程文件） | 84 KB 源码 + 452 KB 编译模块 | 同一量级 |
| 工程目录（含中间产物） | 60 KB | 569 MB | UE5 大 **9500×** |
| 快照消费正确性 | ✓ `EDGEWORLD_GODOT_CHAPTER_ONE_VALID` | ✓ `EDGEWORLD_UE_CHAPTER_ONE_VALID` | 一致 |

`peak_rss_source = time -l (exact child)`：用 macOS `/usr/bin/time -l` 精确测量子进程，
不是 `rusage` 高水位近似。

## 二、结论

1. **冷启动差距是量级性的，不是百分比性的**。UE5 每轮 headless 校验约 10.6 s，Godot 约 0.24 s。
   这不是"引擎好坏"的问题，而是 UE5 启动编辑器级运行时（1.7 GB 内存）对比 Godot 启动一个
   轻量运行时（218 MB）的结构性差异。
2. **第一章本身的载荷几乎一样大**（60 KB vs 84 KB 源码）。**全部成本都在引擎侧**。
3. 因此"用 UE5 做第一章"的真实代价不是代码复杂度，而是**每轮迭代 43× 的等待、128× 的磁盘、
   8× 的内存**。开发期每次验证都要付这个钱。
4. Godot 的引擎是单文件 337 MB，工程 60 KB，**可以整体带着走**；UE5 的 43 GB 安装 + 569 MB
   工程目录，属于重资产。

## 三、未测量的部分（不编造）

| 未测项 | 原因 | 需要什么才能测 |
|---|---|---|
| **帧时间 / FPS** | headless 运行不产生帧，本脚本不渲染 | 需要一个带渲染的采集 harness（两引擎各跑同一场景 N 秒，抓帧时间分布） |
| **资产构建成本** | 未测编辑器级资产构建 | 需要 UE5 资产化关卡（当前 `Content/` 为空，仍用引擎模板地图）与 Godot 导入流程对比 |
| **GPU 表现** | 未接入 GPU 计时 | 需要两引擎各自的 GPU profiler |
| **长期稳定性** | 样本量 3 次/端 | 需要长时间运行与崩溃率统计 |

**不要**在补齐帧时间之前用本页数据宣布"Godot 更好"——本页只证明了**冷启动、内存、磁盘**三项，
这三项对**开发迭代速度**有直接意义，但对**最终画面质量**没有发言权，而画面恰恰是选 UE5 的理由。

## 四、对引擎主线决策的含义

- 若目标是**快速迭代玩法与规则验证**（当前阶段：第一章闭环、定数变数、ECS 漫游）
  → Godot 的 43× 冷启动优势在每轮开发中都会复利，UE5 不适合作为当前主循环。
- 若目标是**最终高清渲染管线**（后期美术、影视级表现）
  → UE5 的 43 GB 与 10.6 s 是可接受的既定成本，但应当在玩法稳定后再投入。
- **建议**：维持现状的分工 —— Godot 为第一章主实现，UE5 为对比实现与后续高清管线候选，
  并由 `tools/validate_godot_ue5_parity.py` 保证两者在同一快照上行为一致，使选型可延后而不返工。
