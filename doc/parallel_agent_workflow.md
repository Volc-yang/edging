# edgeWorld 并行 Agent / Worktree 迭代工作流

本文规定统筹任务与子任务的发布、执行、反馈、上下文更新和提交规则。仓库级约束见根目录 `AGENTS.md`；每轮具体状态见 `doc/parallel_execution_backlog.md`。

## 1. 统一开发原则

1. 优先使用 UE5 发布版成熟引擎与渲染能力，通过发布版插件、Runtime 模块或适配层连接 Genesis 和 edgeWorld 第四维状态演化。
2. 先把已批准的 4D 契约映射到 UE5 发布版能力，以可复现的纵切和证据判断满足与否。
3. 只有发布版方案经实测无法满足已批准契约时，才评估修改 UE5 引擎源码。评估需列明契约缺口、复现证据、插件/旁路替代路径为何失败、改造范围、维护/升级成本和许可影响，由统筹任务批准后才发布源码实现子任务。
4. 未批准的契约草案不得伪装成最终决定；报告明确区分事实、设计建议、验证结果和未决问题。

## 2. 新迭代开始动作

每轮新工作开始时，统筹任务按以下顺序恢复项目上下文：

1. 确认真实 Git 仓库根目录（本项目为 `edge-world/`），运行 `git worktree list --porcelain`、当前分支和状态；不以外层非 Git 项目目录代替仓库。
2. 读取根 `AGENTS.md`、本文和 `doc/parallel_execution_backlog.md`。按任务需要再读取 4D 执行计划、契约 ADR、最近子任务报告和相关代码。
3. 检查已有 Agent/子任务是否运行、完成或等待输入；确认各报告提交号、worktree 路径、当前阶段门以及用户最新决策。
4. 明确本轮目标、基线 SHA、允许触及的文件、用户未提交内容的处理方式、依赖和完成条件。把历史压缩为当前状态、决定、证据缺口和下一动作，不复制已过期的过程叙述。
5. 只有完成以上恢复后才发布新任务。若当前工作区包含任务所需但未提交的内容，优先以只读方式引用原工作区并在任务卡明确；不得默认这些内容存在于从旧提交创建的 worktree。

## 3. Plan mode 与方案树

除非本轮是单一、边界明确且没有有效拆分空间的任务，多 Agent 迭代必须先进行规划轮，再发布实现任务。用户已授权统筹和并行执行时，规划与方案树裁决属于统筹职责，不额外增加用户审批轮。

1. 主任务先给出目标、约束、验收证据、已知上下文和未决问题。规划轮只做调查、方案比较与依赖识别，不与实现混在一起。
2. 每个候选 subagent 提交有边界的执行方案，说明目标/交付物、假设、依赖、文件或接口所有权、步骤顺序、验证证据、风险和未决选择。除非明确安排独立 worktree 写方案文件，规划默认只读。
3. 主任务统筹方案并建立一棵方案树：根节点是迭代目标，下一层为阶段/里程碑，叶节点为子任务；标出依赖边、可并行分支、负责人、交付物和决策门。可用精简大纲或 Mermaid；需要跨轮恢复时写入 backlog 或独立计划文件。
4. 主任务消除路径/接口重叠和相互矛盾的假设，明确标记决定为已接受、暂定或开放，并写明哪些证据可以解锁依赖任务。共享契约未冻结时，只并行调查/提案，不并行实现。
5. 主任务审定方案树后，才从各节点生成实现任务卡。任务卡标注父节点、固定输入和允许改动边界。Agent 可在范围内调整步骤；若要变更共享接口、所有权或关键验收条件，先向主任务汇报并更新方案树。
6. 新证据改变方案树时，只暂停受影响的依赖分支；主任务更新节点、任务卡和上下文，独立完成的工作继续保留。

子任务方案反馈格式：

```text
Proposal ID / parent node:
Objective / deliverable:
Assumptions and fixed inputs:
Dependencies / parallel opportunities:
Owned paths and interfaces:
Ordered execution steps:
Validation and evidence:
Risks / open decisions:
Sizing (optional):
```

## 4. Worktree 与分支规则

- 每个需要写文件的子任务使用单独 worktree 和分支；只读研究也尽量隔离报告写入。
- 建立 worktree 前检查路径、分支和 Git 状态；固定放在仓库 `.worktrees/<task-slug>`，并在 `.git/info/exclude` 忽略该目录，避免把工作树登记成项目源码。
- 每个任务从明确的基线 SHA/分支开始。记录输入文档是提交内容还是单独复制的未跟踪材料；复制输入不等于复制主工作区的所有脏改动。
- 禁止对主工作区执行 `reset`、`clean`、`stash`、强制 checkout 或覆盖操作。不要让多个 Agent 同时写同一文件；共享接口需先由统筹任务冻结。
- 完成的子任务提交到自己的分支，报告 commit SHA。未完成任务不应被描述为已交付；失败/阻塞时报告已完成部分和具体障碍。

## 5. 子任务发布卡

统筹任务给每个 Agent 一张独立任务卡，至少写明：

- 稳定任务 ID、明确目标和为何现在做；
- 依赖项、输入文档/提交及其版本；
- worktree 绝对路径、分支名、基线 SHA；
- 与 UE5 发布版优先原则的关系；
- 允许读/写的路径、明确不允许触碰的路径及文件所有权；
- 交付物路径、完成标准、需要提供的证据和不确定项；
- 是否运行命令/测试（默认不擅自扩大验证范围）；
- 完成时的反馈格式和提交要求。
- 对应的已审定方案树节点/父节点，以及任务类型（规划、实现或审查）。

并行化只用于无依赖或接口已冻结的工作。依赖未满足的实现任务先做调查/设计，不并行猜测不同接口。

### 运行采证与共享 GPU

- 统筹明确交接构建/GPU 所有权。绑定 UI 前先确认目标进程及初始化日志；不能用可能自动启动应用的 UI 入口代替进程检查，避免额外实例污染对照。
- 采证 helper 每次显式接收 run、日志路径、状态目录和真实 PID；操作前核对对应关系，按操作前日志 offset 等待新响应。跨 cell/重启后不复用隐含旧日志或旧 arm 的闭包。
- 原始快照、动作和截图使用 run/attempt 唯一路径，并以独占创建或写前拒绝已存在文件防止覆盖。重试另建 attempt；已丢失的原始记录必须披露并排除，不以相同最终哈希倒推该次操作前状态。
- 工具超时先查原进程和实际新日志，不据观察超时重启活跃实例或判应用失败。保留失败尝试，只重做缺证的检查；返回成功、队列结束和进程退出 0 均不能单独替代任务验收。
- 窗口恢复或进程清理只操作本次精确匹配对象；保留原始 crash/ensure，再处理残留并验证消失，不全局杀进程。应用、启动器、测试报告和工具结果分别记录。

## 6. 子任务反馈格式

Agent 完成时向统筹任务反馈：

1. 状态：完成、部分完成或阻塞；
2. 主要结论和交付物绝对路径；
3. worktree、分支、基线及提交 SHA；
4. 修改文件清单，以及运行过的检查/测试和结果；
5. 未验证项、假设、风险、与其他任务的依赖/冲突；
6. 推荐的下一动作。

统筹任务检查报告和提交差异，必要时追问/返工；未经审查不得将子任务报告说成已集成或阶段门已通过。

## 7. 标准迭代完成动作

每轮统筹任务和本轮子任务都完成后，统筹任务必须：

1. 收齐并检查每个子任务的状态、提交、交付文件和反馈；明确哪些已合并/摘取，哪些仍留在分支，哪些未完成。
2. 综合结论，更新 `doc/parallel_execution_backlog.md`：当前阶段、已验证决策、证据链接、任务状态、阶段门、遗留风险和下一轮动作。删除失效安排，避免上下文膨胀。
3. 需要时更新对应计划/ADR/能力矩阵，保持决策来源和未决状态清楚；不把提案静默升级为批准决策。
4. 只暂存本轮统筹文档和明确获准集成的文件，检查暂存差异；保留所有无关用户改动。
5. 创建一个描述本轮上下文/集成更新的 Git commit，并在反馈中给出提交 SHA、包含文件和未提交内容说明。子任务自己的提交仍保留在其分支，除非明确执行集成。

如果还有本轮 Agent 在运行，则记录为“进行中”并等待反馈；不要提前把轮次标记完成。可先提交纯流程/中间上下文检查点，但必须在 backlog 里标明未完成任务，并在最后一次任务完成后再次执行本节全套收尾动作。

## 8. 下轮上下文维护

上下文文档只保留高价值信息：当前目标、权威决策、当前工作树/分支状态、子任务提交与报告链接、未决问题、下一步依赖。已完成的详细过程留在 Agent 报告和 Git 历史中。新迭代按第 2 节恢复，不要求模型依赖聊天历史才能知道怎么继续。
